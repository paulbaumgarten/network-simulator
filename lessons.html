Lesson 1

The IP model: LAN, subnet and the router as gateway

Introduction

A Local Area Network (LAN) is a group of devices that share the same physical or logical network, such as the computers in one classroom. Every device on an IP network needs an IP address: a numerical label that identifies it. In this simulator the LAN uses addresses that start with 192.168.1. — this is the network prefix. The final number (the host part) is different for each device.

A subnet mask (here 255.255.255.0) tells a device which part of an address is the network and which part is the host. Devices with the same network prefix can talk to each other directly. To reach anything outside the LAN, traffic is sent to the default gateway — the router. The router sits between the LAN and the wider network (the WAN or internet) and forwards traffic between them. In this simulator the router takes address 192.168.1.1 by default.

Exploring in the simulator

  • Add a Router to the canvas and click it. In the configuration panel note its LAN IP (gateway), subnet mask, and WAN IP (public).
  • Add a PC, a Switch, and a Server. Use 🔗 Connect to wire them: PC → Switch → Router → Server.
  • Give devices addresses (the next lesson covers how) and watch the IP appear beneath each device on the canvas.

Tasks

  1. Build a LAN containing at least two PCs, one switch, one router and one server, all connected so that every device has a path to the router.
  2. Select the router and record its LAN IP, its subnet mask, and its WAN IP. Explain to yourself why the LAN and WAN addresses have different prefixes.
  3. Give two PCs addresses and confirm on the canvas that they share the same first three octets (network prefix) but differ in the final octet (host part).

Questions

  1. What is the purpose of the network prefix, and how does the subnet mask 255.255.255.0 separate the network part of an address from the host part?
  2. Two PCs on the LAN have addresses 192.168.1.100 and 192.168.1.150. Are they on the same subnet? Justify your answer using the subnet mask.
  3. What is a default gateway, and why does a PC need to know its gateway's address to reach a device outside the LAN?
  4. The router has both a LAN IP and a separate WAN IP. Explain the role of each.
  5. How many usable host addresses does a /24 network (mask 255.255.255.0) provide, and why is that number not simply 256?
Lesson 2

DHCP: obtaining IP addresses dynamically

Introduction

Assigning an address to every device by hand does not scale. The Dynamic Host Configuration Protocol (DHCP) automates this. A DHCP server holds a pool of available addresses and hands one out to each device that asks. The assignment is called a lease: it is temporary and can be returned (released) when no longer needed. Along with an IP address, DHCP also supplies the gateway address and the address of the DNS server the client should use.

In this simulator the router runs the DHCP server. Its default pool is 192.168.1.100 to 192.168.1.199. When a PC requests an address, the server picks the lowest free number in the pool and records the lease.

Exploring in the simulator

  • Select the router and find the DHCP Server section. Confirm the toggle is on and read the Pool range and Active leases count.
  • Select a PC and click 📥 Request IP (DHCP). Watch the cyan handshake animation travel to the router and back before the lease is confirmed in the log.
  • Note that a PC which is not connected to the router by any path cannot receive a lease — the simulator reports this in the feedback log.
Observe The DHCP exchange is shown with cyan packets. After a successful lease, the PC's IP, gateway and DNS values populate in its configuration panel and its IP appears on the canvas.

Tasks

  1. Lease addresses to three PCs one after another. Record the address each one receives and confirm they are allocated in ascending order from the pool.
  2. Release one PC's lease, then have a new PC request an address. Observe which address the new PC is given and explain the result.
  3. Disconnect a PC from the network (delete its link), then attempt a DHCP request. Record the message the simulator returns and why it occurs.

Questions

  1. List the four pieces of configuration a client typically receives from DHCP in this simulator, and state what each is used for.
  2. Why is an address described as a "lease" rather than a permanent assignment? Give one advantage of leasing.
  3. The default pool runs from .100 to .199. What is the maximum number of devices that can hold a lease at once, and what happens when the pool is exhausted?
  4. Why must a client be able to reach the DHCP server over the network before it can obtain an address? (Consider that it has no IP yet.)
  5. Give one reason a network administrator might choose to reserve part of the address range outside the DHCP pool for manual assignment.
Lesson 3

DNS: zones, A and CNAME records, and resolution

Introduction

People remember names such as www.myschool.local, but networks route traffic using IP addresses. The Domain Name System (DNS) translates between the two. A DNS server holds records that map names to addresses. The two most common record types are:

  • A record — maps a name directly to an IPv4 address, for example www.myschool.local → 192.168.1.101.
  • CNAME record — maps a name to another name (an alias), for example portal.myschool.local → www.myschool.local. Resolving a CNAME means following it to the target name and then resolving that.

Resolution is the process of starting with a name and ending with an IP address. If a name points to a CNAME, the resolver follows the chain until it reaches an A record.

Exploring in the simulator

  • Select a server that has an IP address and enable the DNS service. A DNS Zone Records editor appears.
  • Add an A record mapping a domain to the server's own IP address. Add a CNAME record that points a second name at the first.
  • Select a PC and use the nslookup field (or the terminal, covered in Lesson 5) to resolve each name. The feedback log shows the resolution chain step by step.

Tasks

  1. Create an A record for www.myschool.local that points to your web server's IP, then resolve it from a PC and record the returned address.
  2. Add a CNAME record for portal.myschool.local pointing to www.myschool.local. Resolve portal.myschool.local and record the full chain shown in the log.
  3. Resolve a name for which no record exists. Record the exact error and explain what it means.

Questions

  1. Explain the difference between an A record and a CNAME record, and give an example use for each.
  2. When you resolved portal.myschool.local, describe the sequence of steps the resolver took to reach a final IP address.
  3. Why might using a CNAME be more maintainable than creating several separate A records when one server hosts several named sites?
  4. What happens to name resolution across the whole network if the DNS server is switched off or becomes unreachable? What could still work, and how?
  5. The resolver limits how many CNAMEs it will follow. Why is such a limit necessary?
Lesson 4

Web servers: hosting page content

Introduction

A web server is software running on a host that responds to requests for web pages. A client sends an HTTP request (for example GET /) and the server returns a response: a status line such as 200 OK, some headers, and the page content (HTML). Web traffic uses port 80 for plain HTTP and port 443 for encrypted HTTPS.

In this simulator a server can host a single page. You edit the HTML directly, and clients can fetch it with the curl command or view it rendered in the built-in browser.

Exploring in the simulator

  • Select a server with an IP address and enable the Web service. Note the ports listed: 80 and 443.
  • Edit the Web Page Content HTML. Keep it simple to begin with, for example a heading and a paragraph.
  • Open a PC's terminal and run curl http://<server-ip>, then switch to the Browser tab to see the page rendered.
Tip For readable URLs, combine this with Lesson 3: add a DNS A record for your server, then request the page by name instead of by IP address.

Tasks

  1. Host a page with a heading, a paragraph and a list. Fetch it with curl and confirm the returned HTML matches what you entered.
  2. Add a DNS record so the page can be reached by name, then load it in the Browser tab using that name.
  3. Turn the Web service off and attempt to load the page again. Record the exact message the client receives and relate it to the idea of a port being closed.

Questions

  1. Describe the request/response cycle for a single web page, naming the request method and the meaning of a 200 OK status.
  2. Which port does plain HTTP use, and which port does HTTPS use? Why does it matter that these are different?
  3. When the Web service was disabled, what response did the client get, and what does this tell you about how servers handle requests to closed ports?
  4. Why is it useful to reach a website by name rather than by IP address, both for users and for the site operator?
  5. The simulator serves one page per server. In reality a web server hosts many resources. What role do the parts of a URL after the host name (the path) play in selecting a resource?
Lesson 5

The terminal: ping, nslookup, curl, ipconfig

Introduction

Network engineers diagnose problems using command-line tools. Each PC in the simulator has a terminal offering the core commands:

  • ipconfig — shows this PC's own IP address, subnet mask, gateway and DNS server.
  • ping [ip|domain] — tests whether another host is reachable and reports round-trip times.
  • nslookup [domain] — asks the DNS server to resolve a name to an address.
  • curl http(s)://domain — fetches a web page and prints the response.
  • help — lists the available commands.

Because each command drives the real simulation, its output reflects the network you actually built — including failures when something is misconfigured.

Exploring in the simulator

  • Select a PC and click 🖥 Open Terminal / Browser. Run help to see every command.
  • Run ipconfig to confirm the PC's addressing, then ping another device by its IP address.
  • Use nslookup on a domain you created, then curl that same domain and compare what each command tells you.

Tasks

  1. Use ipconfig to record your PC's IP, gateway and DNS values. Then ping the gateway and record the reported round-trip time and TTL.
  2. Resolve a domain with nslookup, note the IP returned, then ping that IP directly. Confirm the name and the address reach the same host.
  3. Run curl against a domain before, and then after, disabling either DNS or the web service. Record how the error message differs between the two failures.

Questions

  1. What information does ipconfig report, and why is it usually the first command to run when a PC cannot reach the network?
  2. ping can succeed while curl fails for the same host. Give a scenario in which this happens and explain why.
  3. What is the difference between what nslookup tests and what curl tests? Which layer of activity does each exercise?
  4. You ping a domain name and it fails, but pinging its IP address succeeds. What does this tell you about where the problem lies?
  5. Why is it valuable that these commands operate on the network you built, rather than returning fixed sample output?
Lesson 6

Firewalls and filtering traffic

Introduction

A firewall controls which traffic is allowed to pass through a point in the network. It applies a list of rules, each stating whether to allow or block traffic that matches a destination IP address and port. Rules are evaluated in order from top to bottom, and the first matching rule wins. If no rule matches, a default action applies.

A secure design usually follows default-deny: block everything by default, then add specific allow rules only for the services that are genuinely needed. This is the opposite of default-allow, where everything is permitted unless explicitly blocked.

In this simulator the firewall runs on the router. Blocked traffic is shown as a red packet that is dropped when it reaches the router, and the reason is reported in the log and terminal.

Exploring in the simulator

  • Select the router and open the Firewall section. Enable it and note the default action.
  • Add a rule such as BLOCK any : 80 to block all plain HTTP traffic, then try to curl an HTTP site from a PC.
  • Change the default action to BLOCK and add explicit ALLOW rules for the ports you want, observing how traffic is affected.
Watch the colour When a packet is blocked it turns red and is dropped exactly at the firewall. The terminal names the rule responsible, which helps you debug your rule order.

Tasks

  1. Block port 80 while leaving port 443 open. Confirm that curl http://… is dropped but curl https://… (with a valid certificate) still works.
  2. Switch to a default-deny posture: set the default action to BLOCK, then add a single ALLOW rule for port 443. Verify which requests now succeed.
  3. Create two rules that both match the same traffic but have opposite actions. Reorder them and record how the outcome changes, demonstrating that the first match wins.

Questions

  1. Explain the difference between a default-allow and a default-deny firewall, and state which is generally more secure and why.
  2. Rules are evaluated top to bottom with the first match winning. Why does the order of rules matter? Give an example where a poorly ordered rule set fails to achieve its intent.
  3. You blocked port 80 but a PC can still reach the site over port 443. Explain why blocking one port does not necessarily block a service entirely.
  4. A firewall that is enabled but set to default-allow with no block rules provides little protection. Explain why.
  5. Give one advantage and one limitation of filtering traffic purely by IP address and port number.
Lesson 7

TLS certificates and Let's Encrypt

Introduction

HTTPS is HTTP carried over an encrypted TLS connection. To offer HTTPS, a server presents a certificate: a signed statement that binds a domain name to the server's identity. A certificate is issued by a Certificate Authority (CA) that browsers trust. Let's Encrypt is a widely used CA that issues certificates automatically and at no cost.

A certificate carries a validity period with an issue date and an expiry date, and it names the domain it is valid for. When a client connects over HTTPS it checks three things: that a certificate is present, that it has not expired, and that its domain matches the site being visited. If any check fails, the connection is not trusted.

Exploring in the simulator

  • Select a web server and find the SSL / TLS Certificate module. Enter the domain your site uses (matching your DNS record).
  • Click 🔒 Generate certificate to issue a valid Let's Encrypt certificate. Read the issuer, issue date and expiry shown in the status box.
  • From a PC, curl https://<your-domain> and observe the TLS handshake line and the padlocked (green) packets.

Tasks

  1. Issue a valid certificate for your domain, then load the site over HTTPS in the browser. Confirm the lock indicator shows the connection as secure.
  2. Enable Force HTTPS on the web server, then attempt to load the site over plain HTTP. Record what happens and why.
  3. Issue a certificate for one domain but request the site using a different domain name that also points to the same server. Record the validation result and explain it.

Questions

  1. What three checks does a client perform on a certificate during an HTTPS connection, and what does each one protect against?
  2. What is the role of a Certificate Authority, and why must the client already trust the CA for the certificate to be meaningful?
  3. Explain what "domain match" means and why a certificate issued for one domain should not be accepted for another.
  4. Why do certificates have an expiry date rather than lasting forever? Give a security reason.
  5. What does the Force HTTPS setting achieve, and why might a site operator enable it?
Lesson 8

Denial of service (DDoS) and rate limiting

Introduction

A Denial of Service (DoS) attack aims to make a service unavailable to its legitimate users. A Distributed Denial of Service (DDoS) attack does this from many sources at once, flooding the target with more requests than it can handle. The target's server, or the single network link leading to it, becomes a bottleneck that is overwhelmed.

Defences include rate limiting (capping how many requests a source may send in a period), filtering unwanted traffic at the firewall or upstream, using a content delivery network or scrubbing service to absorb the load, and provisioning redundant capacity so there is no single point of failure.

Exploring in the simulator

  • Build a network with a web server and several PCs. Open 🛡 Pen-Test and run the assessment.
  • Find the DDoS finding and click ▶ Demonstrate attack to watch a flood of red packets converge on the server.
  • Enable the firewall on the router and run the assessment again. Compare the severity of the DDoS finding before and after.
Observe The demonstration launches repeated bursts of packets from every available source toward the server, illustrating how a single target and a single uplink become saturated.

Tasks

  1. Run the DDoS demonstration against your web server and describe what the flood of packets represents in a real attack.
  2. Run the pen-test with no firewall enabled and record the DDoS severity rating. Enable the firewall and re-run; record the new rating.
  3. Identify the single points of failure in your topology (the server and the links leading to it) and describe one change to the design that would reduce the impact of a flood.

Questions

  1. Distinguish between a DoS and a DDoS attack. Why is the distributed form harder to defend against?
  2. What is a bottleneck in the context of this attack, and where are the bottlenecks in your simulated network?
  3. The simulator rates DDoS resilience as slightly better when a firewall is present but still not fully protected. Explain why a firewall alone is insufficient against a large volumetric attack.
  4. Explain how rate limiting reduces the effect of a flood, and give one drawback of setting the limit too low.
  5. Why does adding redundant capacity or an upstream scrubbing service help, when simply making one server larger may not?
Lesson 9

Man-in-the-middle interception

Introduction

A man-in-the-middle (MITM) attacker positions themselves on the path between a client and a server, where they can read or alter traffic as it passes. Whether this matters depends on whether the traffic is encrypted. Plaintext traffic (such as plain HTTP) can be read directly by anyone on the path, including passwords and page content. Encrypted traffic (such as HTTPS) appears as unreadable data, so an interceptor learns little from it.

The simulator lets you place an eavesdropper on the network and compare, side by side, what the attacker sees for HTTP versus HTTPS.

Exploring in the simulator

  • Enable the 🕵️ MITM toggle in the toolbar. A banner appears on the canvas indicating an eavesdropper is active.
  • From a PC, curl a site over HTTP. Observe that the packets are red and the interceptor displays the readable payload.
  • Issue a certificate (Lesson 7), then curl the same site over HTTPS. Observe that the packets are green with a padlock and the interceptor sees only ••••••••.

Tasks

  1. With MITM active, request a page over HTTP and record exactly what the eavesdropper is shown next to the packets.
  2. Repeat the request over HTTPS with a valid certificate and record what the eavesdropper is shown this time.
  3. Read the terminal and feedback log after each request. Record the specific message the simulator gives about whether the traffic could be read.

Questions

  1. What is a man-in-the-middle attacker, and what position on the network do they need to occupy?
  2. Using your observations, contrast what the interceptor could read for HTTP versus HTTPS traffic.
  3. Encryption protects the content of traffic, but an interceptor may still observe some information about a connection. Suggest what an attacker might still learn even when traffic is encrypted.
  4. Why is it dangerous to enter a password on a site served over plain HTTP, particularly on a shared or public network?
  5. Explain how HTTPS defends against a man-in-the-middle, referring both to encryption and to the certificate check from Lesson 7.
Lesson 10

Unsecured protocols (ports 80, 21, 25)

Introduction

Several long-established protocols transmit data, and often credentials, without encryption by default. In this simulator the relevant services and ports are:

  • HTTP — port 80: web pages in plaintext.
  • FTP — port 21: file transfer, historically with credentials sent in the clear.
  • SMTP — port 25: email transfer between servers, unencrypted in its basic form.

Each of these has a secure replacement or extension (for example HTTPS, FTPS/SFTP, and SMTP with STARTTLS). Leaving the unencrypted versions open increases the attack surface: the set of points where an attacker could interact with your system.

Exploring in the simulator

  • On a server, enable the File service (port 21) and the Mail service (port 25). Note the ports shown for each.
  • Run the 🛡 Pen-Test assessment and read the finding about legacy clear-text services.
  • Combine this with Lesson 9: enable MITM and observe that any traffic on these unencrypted protocols is exposed.

Tasks

  1. Enable the File and Mail services and record the ports the simulator associates with each.
  2. Run the pen-test and record the severity and remediation advice given for the unsecured-protocol finding.
  3. Add firewall rules that block ports 21 and 25 from untrusted sources, re-run the pen-test, and note any change in the findings.

Questions

  1. For each of ports 80, 21 and 25, name the protocol and state what kind of data it carries.
  2. What does the term "attack surface" mean, and how does leaving unencrypted services open increase it?
  3. For one of the three protocols, name its secure alternative and explain what that alternative adds.
  4. Blocking a port at the firewall and switching to an encrypted protocol are two different responses. Explain the difference and when you might use each.
  5. Why might an organisation still be running these legacy protocols despite the risks, and what makes migrating away from them difficult?
Lesson 11

Application attacks: phishing, SQL injection, XSS

Introduction

Not every attack targets the network layer. Many target the application — the website itself and the people who use it.

  • Phishing tricks users into trusting a fraudulent site or message. Without HTTPS and a valid certificate, users have no reliable way to confirm they are on the genuine site.
  • SQL injection (SQLi) occurs when user input is placed directly into a database query. Crafted input can change the query's meaning, exposing or altering data. The defence is to validate input and use parameterised (prepared) queries.
  • Cross-site scripting (XSS) occurs when a site displays untrusted input without escaping it, allowing an attacker's script to run in another user's browser. The defence is to escape or encode output.

The simulator inspects your hosted HTML for signs of these weaknesses: script or event-handler markup suggests an XSS risk, and input forms suggest a surface where SQL injection must be considered.

Exploring in the simulator

  • Edit a web server's page to include a form (<form> and <input> elements) and, separately, some script or an inline event handler.
  • Run the 🛡 Pen-Test assessment and read the injection findings it raises.
  • Remove the site's certificate (or leave it without one) and note the phishing-related finding about users being unable to verify authenticity.
Note The simulator's browser strips scripts before rendering, so no real code executes. The pen-test flags the pattern in your content to teach you where the risk would be.

Tasks

  1. Add a login-style form to your page, run the pen-test, and record the SQL-injection-related finding and its recommended remediation.
  2. Add script or event-handler markup to your page, run the pen-test, and record the XSS finding and its severity.
  3. Leave the site without a certificate, run the pen-test, and record the phishing finding. Then issue a certificate and confirm the finding is resolved.

Questions

  1. Explain how phishing exploits a user's inability to verify a site's identity, and how HTTPS with a valid certificate helps.
  2. Describe how SQL injection works at a high level, and explain why parameterised queries prevent it.
  3. Describe how cross-site scripting works, and explain what "escaping output" means and why it defends against XSS.
  4. SQL injection and XSS both stem from mixing untrusted input with something else (a query, or a page). Explain the common underlying cause and the general principle that prevents both.
  5. Why are application-layer attacks not stopped by a network firewall that filters on IP address and port alone?
Lesson 12

Expired and missing certificates

Introduction

A certificate only provides protection while it is valid and correctly matched to the site. Three common failures break this:

  • Missing certificate: the server offers no certificate, so a secure connection cannot be established at all.
  • Expired certificate: the certificate's expiry date has passed. Clients no longer trust it, even though it was once valid.
  • Self-signed certificate: the certificate is signed by the server itself rather than a trusted CA, so clients cannot verify its authenticity and show a warning.

Each failure produces a browser warning or a refused connection. Training users to "click through" such warnings is itself a security risk, because it teaches them to ignore genuine danger signs.

Exploring in the simulator

  • On a web server, use the SSL module's options to issue an Expired (demo) certificate and a Self-signed certificate, and also try the case with no certificate.
  • For each case, curl https://<your-domain> from a PC and read the validation message. Also load the site in the Browser tab and observe the warning page and lock indicator.
  • Run the 🛡 Pen-Test assessment and find the certificate-related findings.

Tasks

  1. Test all three failure cases (missing, expired, self-signed). For each, record the exact validation message the simulator reports.
  2. Load one failing case in the Browser tab and describe how the warning page and lock indicator differ from a valid HTTPS connection.
  3. Re-issue a valid certificate for the correct domain and confirm that both curl and the browser now treat the connection as secure.

Questions

  1. Distinguish between a missing, an expired and a self-signed certificate, and describe the client's response to each.
  2. Why does a certificate that was valid yesterday stop being trusted once its expiry date passes?
  3. A self-signed certificate still encrypts the connection. Explain why clients nonetheless warn about it, referring to the role of the Certificate Authority.
  4. Why is it a security problem when users become accustomed to clicking past certificate warnings?
  5. Automated issuance and renewal (as offered by Let's Encrypt) directly address one of these failures. Which one, and how?
